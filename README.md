# Meridian Retail Support-Draft Review Tool

A small classroom demo. It drafts a customer support reply for one
fictional case at a time, using only the facts in `cases.json` and the
rules in `policy.md`, and prints it for a human reviewer. It calls a
**local** model via [Ollama](https://ollama.com) — no cloud API key needed.

This tool **only prints text**. It never sends messages, approves refunds,
or changes any records (policy P4). A person must review every draft
before acting on it.

## Files

- `policy.md` — the drafting policy the model must follow.
- `cases.json` — three fictional support cases (C1, C2, C3).
- `app.py` — CLI entry point. Loads the chosen case and the policy, calls
  the local model via Ollama, validates its response, and prints three
  labelled sections.
- `setup_env.py` — interactively prompts for the Ollama host and model
  (both have sane defaults), and writes a project-local `.env`. Neither
  value is a secret — Ollama has no API key.
- `.env.example` / `.env` — where the host and model live (`.env` is
  gitignored).
- `requirements.txt` — pinned Python dependencies.
- `demo_outputs.json` — prerecorded synthetic results used only by
  `--offline-demo`. Not generated by calling a model.
- `test_app.py`, `test_setup_env.py` — unit tests (no network calls, no
  Ollama installation required to run them).

## Setup

1. Install Ollama (macOS: `brew install ollama`, or download from
   [ollama.com](https://ollama.com)) and make sure it's running:

   ```bash
   ollama serve   # if it isn't already running as a background service
   ```

2. Pull the model this tool defaults to:

   ```bash
   ollama pull llama3.2
   ```

3. Set up the Python side:

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   python setup_env.py
   ```

   `setup_env.py` asks for the Ollama host (default
   `http://localhost:11434`) and model (default `llama3.2`), and writes
   both into a local `.env`.

## Running

```bash
python app.py --case C1
```

`--case` is required and must be `C1`, `C2`, or `C3`. Every run prints
three sections: `SUPPLIED FACTS`, `SUPPLIED POLICY`, and
`DRAFT RESULT FOR HUMAN REVIEW` (`review_status`, `draft_reply`,
`evidence_refs`, `missing_information`).

Two flags bypass the live model entirely, for demoing without Ollama
running:

```bash
python app.py --case C1 --offline-demo       # loads a prerecorded result
python app.py --case C1 --simulate-timeout   # shows the safe unavailable state
```

If `C2` is selected (its `delivery_date` is missing), the app never calls
the model at all — it returns a deterministic "please provide the delivery
date" result per policy P2.

If the real call to Ollama fails (not running, model not pulled, timed
out) or the model returns something that doesn't match the required JSON
schema, the tool shows the same safe unavailable state
(`review_status: UNAVAILABLE`, empty draft) with a manual-fallback message
— never a traceback or a stale draft.

The app reads the model only from `APP_OLLAMA_MODEL` (default `llama3.2`)
and the server address only from `APP_OLLAMA_HOST` (default
`http://localhost:11434`).

## Testing

```bash
pytest
```

Tests use a fake model function and fake input readers throughout — no
real Ollama calls are made and Ollama does not need to be installed to run
them. They cover a successful draft, invalid model output, a simulated
provider timeout, the deterministic missing-delivery-date path, all three
input files, offline-demo output, and `setup_env.py`'s `.env` writing.
